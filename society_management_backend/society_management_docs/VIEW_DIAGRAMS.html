4. Phase 2: Login & Multi-Role / Multi-Society Selection Popup
Selection Flow

When a user logs in with their phone number, the backend detects if they hold multiple roles/flats across societies. The app presents an interactive popup to select the desired active role and scopes subsequent API requests accordingly.

sequenceDiagram autonumber actor User as User (Phone Number) participant App as Mobile App participant API as Laravel Backend participant DB as Database (Multi-Tenant) User->>App: Enter Phone Number + Password / OTP App->>API: POST /login (phone, password/otp) API->>DB: Query user by phone & fetch all approved memberships in user_societies DB-->>API: Return User + array of available_profiles[] (roles, societies, flats) API-->>App: Return Bearer Token + available_profiles[] + requires_role_selection alt Case 1: Phone Number has Multiple Roles / Flats (count > 1) App->>User: Display Popup Modal: "Select Role & Profile to Continue"
(e.g., [Secretary - Green Valley] vs [Owner - Flat A-102] vs [Tenant - Flat C-304]) User->>App: Taps Selected Role / Profile Card else Case 2: Single Role (count == 1) App->>App: Auto-select single linked profile end App->>API: GET /dashboard (Headers: X-Society-Id, X-Active-Role, X-Flat-Id) API->>DB: Scoped query for active society, role & flat DB-->>API: Return customized profile dashboard API-->>App: Render Role-Specific Dashboard (Admin vs Owner vs Tenant) opt Switch Role Later User->>App: Taps "Switch Role / Flat" in Account Hub App->>User: Reopens Role Selection Popup Modal User->>App: Selects alternate role -> App updates active context headers end

Sequence Diagram

Categorizes flat-specific visitors (photo + target flat + auto resident push alert) vs. maintenance staff (basic details only, no photo, multi-flat access).
